1. Product vision

Developers accumulate small, high-value fragments of knowledge — curl commands, shell one-liners, config snippets, debugging notes — scattered across notes apps with no reliable way to retrieve them later. Filaway is a macOS notes app with the capture simplicity of Apple Notes, where an AI silently organizes everything after each writing session and retrieval works through natural language (“the curl command I used two days ago”).

Product principles (binding on all phases):

  1. Capture is sacred. Writing must be instant, blank-page, zero-decision. The AI never interferes while the user is typing.
  2. The AI shows its work. Every automated action is visible, summarized, reversible (undo), and inspectable (diff).
  3. The user's data is plain files on their disk. No proprietary database lock-in for note content. The user can open their notes folder in Finder and read everything.
  4. Local-first. The app is fully usable offline for capture and browsing; AI features degrade gracefully when the provider is unreachable.

2. Scope of this document

  • Phase 1 is specified in full (Sections 4–10) with UX mockups (Figures 1–4). This is the build target.
  • Phases 2–4 are outlined at feature level only (Section 11), so architectural decisions in the design spec do not paint us into a corner.

3. Target user and platform

  • User: An individual software developer on macOS. Single user, single machine, no collaboration.
  • Platform (Phase 1): macOS 14 (Sonoma) or later, Apple Silicon and Intel.
  • Distribution (Phase 1): Downloadable DMG from a website. Signed and notarized so Gatekeeper accepts it. Mac App Store distribution is explicitly out of scope for Phase 1 (sandboxing constraints conflict with plain-folder storage; revisit in a later phase).

4. Phase 1 — Functional requirements

Requirement IDs use the pattern FR-x.y. Priorities: MUST Phase 1 launch blocker · SHOULD Phase 1 if time permits · COULD nice to have.

4.1 Application shell and layout → Figure 1

FR-1.1MUST The app presents a two-pane window: a left sidebar and a right editor pane, per Figure 1 (Apple Notes-like aesthetic: light chrome, generous whitespace, native macOS feel).
FR-1.2MUST The sidebar has two sections: Recents (top) — notes ordered by last-opened/last-edited time, most recent first, title + relative timestamp, capped at ~10 items, purely chronological, never reordered by AI; and Library (bottom) — a collapsible tree of folders and notes, AI-managed (4.4) but fully browsable and manually editable by the user.
FR-1.3MUST A search/command bar is accessible at all times, both as a visible toolbar field and via in-app shortcut (⌘K). See 4.5.
FR-1.4MUST A “New note” action (⌘N and toolbar button) opens a blank untitled note with focus in the body, ready to type. No dialogs, no required metadata.
FR-1.5SHOULD Window state (size, sidebar width, last open note) persists across launches.

4.2 Editor

FR-2.1MUST Plain-text-first editing with lightweight formatting: headings, bold/italic, bulleted and numbered lists, checkboxes, and fenced code blocks. Markdown is the storage format (Section 5); whether the editor renders Markdown live or shows styled text is a design-spec decision.
FR-2.2MUST Code blocks are first-class: monospaced, visually distinct, one-click “Copy” affordance (Figure 1), optional language tag. Commands/snippets are the core retrieval object.
FR-2.3MUST Autosave. No explicit Save action; content persists continuously (target: ≤ 2 seconds of typed content lost on force-quit).
FR-2.4SHOULD Paste intelligence: pasting content that looks like a shell command or code offers to wrap it in a code block.
FR-2.5COULD Attachments (images) embedded in notes. If deferred, the design spec should state how the storage format will accommodate them later.

4.3 Writing session model

FR-3.1MUST A “writing session” begins when the user starts editing any note and ends when all of the following hold: no keystrokes in the editor for a configurable idle interval (default 3 minutes, range 1–15), and the note is not frontmost-with-focus being actively scrolled/selected. Switching away from the app or closing the window also ends the session immediately.
FR-3.2MUST Session end triggers the AI organization pipeline (4.4) for content written in that session. Organization runs in the background; the user can keep using the app, including resuming typing in the same note (which cancels or supersedes the pending organization for that note — exact semantics defined in the design spec, but the user must never lose text).

4.4 AI organization → Figure 2a

FR-4.1MUST After a session ends, the AI analyzes the session's content and produces an organization plan consisting of zero or more actions from this closed set: create a new note (with AI-generated title) in a Library folder; append/merge session content into an existing note; create a new folder in the Library (max depth: 2 levels); move a note between folders; retitle an untitled note; tag content (freeform tags stored in note metadata).
FR-4.2MUST Two operating modes, user-selectable in Settings: Ask before filing (default) — the plan is presented as a non-blocking card (“Merge code block into Commands/curl?”) with Accept / Edit / Dismiss; nothing changes until accepted. Auto-file — the plan is applied immediately, then summarized in the same card style with Undo and View changes (Figure 2a).
FR-4.3MUST Every applied plan is fully reversible via a single Undo for at least the last 10 organization events, and an “Activity” log lists all AI actions with timestamps and a diff view (before/after of affected notes).
FR-4.4MUST The AI never deletes user content. Merging must be additive (content appended with a divider/heading, or interleaved only if the user accepts an explicit merge preview). Original raw session text remains recoverable via the Activity log for at least 30 days.
FR-4.5MUST The user can exclude folders from AI processing entirely (organization and search indexing). Excluded content is never sent to the AI provider.
FR-4.6SHOULD The Library taxonomy should converge rather than sprawl: the AI prefers existing folders/notes over creating new ones, and proposes folder renames/merges (as plans, never silently) when structure fragments.
FR-4.7COULD A “Reorganize library” command the user can run on demand over the whole corpus.

4.5 Search and retrieval → Figure 2b

FR-5.1MUST One search bar, two behaviors. Keyword mode: as-you-type literal/fuzzy filtering over titles and body text, instant (<100 ms perceived), fully offline, no AI involved. Semantic mode: natural-language queries (“curl command to fetch documents”, “the thing I edited two days ago about auth”) answered using AI + a local semantic index. Trigger heuristics (question-like phrasing, explicit toggle, or Enter on a multi-word query) are a design-spec decision, but both modes must be reachable without mode-switching friction.
FR-5.2MUST Semantic results present a best-match answer card when the answer is a snippet/command (Figure 2b): the snippet rendered as a code block with one-click Copy, plus source note and last-edited time; below it, a ranked list of matching notes. Clicking any result opens the note scrolled to the relevant section.
FR-5.3MUST Temporal queries are supported: “two days ago”, “last week”, “yesterday” filter/boost by note edit timestamps.
FR-5.4MUST The semantic index updates incrementally as notes change; a full reindex command exists in Settings.
FR-5.5SHOULD Keyword search works even when the AI provider is unreachable; the UI states clearly that semantic answers are unavailable offline.

4.6 AI provider connection → Figures 3 & 4

FR-6.1MUST Phase 1 supports exactly one provider: Anthropic Claude via the user's own API key. First-run onboarding includes a “Connect your AI” step (Figure 3): paste key → validate with a test call → confirm. The key is stored in the macOS Keychain, never in plain files.
FR-6.2MUST Settings → AI (Figure 4) shows connection status, selected model, and lets the user replace or remove the key. Model selection may be a fixed sensible default with an “advanced” override; the design spec chooses the default model balancing cost/quality for organization and search tasks.
FR-6.3MUST A visible privacy statement in onboarding and Settings: notes live on local disk; only the text needed for organization/search is sent to the provider; excluded folders are never sent.
FR-6.4MUST Graceful degradation: invalid key, rate limits, network failure, or provider outage must never block capture, browsing, or keyword search. AI features queue or disable with clear, non-nagging status.
FR-6.5SHOULD The onboarding UI shows “Local model (Ollama)” as a visible-but-disabled option labeled for a future version (Figure 3), so the provider abstraction is designed in from the start (Section 11, NFR-5).
FR-6.6SHOULD A monthly cost/usage indicator (approximate tokens or request count) in Settings, since the user pays for their own API usage.

4.7 Onboarding (first run)

FR-7.1MUST Three steps maximum: (1) welcome + choose/confirm notes folder location (default ~/Notes or similar), (2) connect AI (Figure 3), (3) quick orientation of the sidebar/search. Skippable where safe; the app must be usable with AI connection skipped (capture + keyword search only, with a persistent gentle prompt to connect).
FR-7.2SHOULD Optional import from Apple Notes at first run or later (via Apple Notes export or automation), preserving note titles and bodies. If deferred to Phase 1.x, the design spec says so with a stub.

4.8 Settings

FR-8.1MUST Settings pane covering: AI provider (4.6), idle interval, organization mode (ask/auto), excluded folders, notes folder location, semantic search on/off, reindex, and Activity log access (Figure 4 shows the AI section).

5. Data and storage (Phase 1)

DS-1MUST Note content is stored as plain Markdown files in a user-visible folder (default ~/Notes), with the Library folder tree mirrored as real subdirectories. Rationale: user ownership (Principle 3) and it makes Phase 2 sync (Google Drive et al.) a matter of pointing sync at a folder rather than inventing a sync protocol.
DS-2MUST Per-note metadata (tags, created/edited timestamps, AI provenance) is stored either as Markdown front-matter or in a sidecar index — design-spec decision — but the Markdown body must remain cleanly readable in any text editor.
DS-3MUST Derived data (semantic index/embeddings, activity log, undo history) lives in the app's Application Support directory, is rebuildable from the notes folder, and is explicitly not part of the user's owned data.
DS-4MUST External edits tolerated: if the user edits/adds/removes files in the notes folder outside the app, the app detects changes on next launch (or live, design-spec decision) and reconciles without data loss.
DS-5MUST No user content in any cloud service except transient API calls to the AI provider.

6. Non-functional requirements (Phase 1)

IDRequirement
NFR-1 PerformanceCold launch to editable note < 2 s on Apple Silicon. Keyword search results < 100 ms perceived. Semantic answers < 5 s typical.
NFR-2 ScaleSmooth with 5,000 notes / 50 MB of Markdown; degrade gracefully to 20,000 notes.
NFR-3 ReliabilityNo data loss on crash beyond FR-2.3's 2-second window. AI failures never corrupt or lose notes.
NFR-4 Privacy/SecurityAPI key in Keychain; TLS for all provider calls; no analytics that include note content; any telemetry is opt-in and content-free.
NFR-5 ExtensibilityAI provider integration sits behind an internal abstraction so additional providers (local Ollama, other cloud APIs) are additive. Storage paths must not assume ~/Notes is on the boot volume (Phase 2 points it at synced folders).
NFR-6 AccessibilityStandard macOS accessibility (VoiceOver labels, full keyboard navigation, respects system text-size settings where feasible).
NFR-7 Native feelFollows macOS Human Interface Guidelines; light and dark mode support.

7. Out of scope for Phase 1 (explicit)

  • Multi-device sync of any kind; iCloud; Google Drive.
  • Windows/Linux builds.
  • Collaboration, sharing, publishing.
  • Mobile apps.
  • Local LLM inference (UI placeholder only, per FR-6.5).
  • Mac App Store distribution.
  • End-to-end encryption of the notes folder (files are as secure as the user's disk; FileVault is assumed).

8. Success criteria for Phase 1

  • A user can install from DMG, connect a Claude API key, and be typing a note within 3 minutes of download.
  • After a week of normal use, retrieval test: the user can find a specific stored command via natural language in under 10 seconds, ≥ 90% of the time on their own corpus.
  • Zero instances of AI-caused content loss in testing.
  • The user can quit the app, open ~/Notes in a text editor, and read everything.

9. Open questions for the design specification

The design spec (produced by the receiving agent) should decide and justify at least:

  1. Implementation stack (native Swift/SwiftUI vs. alternatives) given NFR-7 and the DMG distribution target.
  2. Editor approach: live Markdown rendering vs. rich-text-over-Markdown, and which component/library.
  3. Semantic index design: embedding model choice (via Claude-compatible pipeline or local embedding model), index storage, incremental update strategy — noting that keyword search must remain fully local.
  4. Session/organization pipeline concurrency model and conflict semantics (FR-3.2).
  5. Metadata storage (front-matter vs. sidecar) per DS-2.
  6. File-watching/reconciliation strategy per DS-4.
  7. Testing strategy: unit, integration (including AI-call mocking/recording), UI automation, and a corpus-based retrieval quality benchmark for FR-5.x; how NFR-1/2 performance budgets are enforced in CI.
  8. Update mechanism for a non-App-Store app (e.g., Sparkle or equivalent) — required for shipping fixes.
  9. Crash reporting/diagnostics consistent with NFR-4.
  10. Prompt/versioning strategy for the organization and search prompts, and how prompt changes are tested against regressions.

10. Phase 1 milestone suggestion (indicative, not binding)

  1. M1 — Capture core: shell, sidebar, editor, autosave, plain-folder storage, keyword search.
  2. M2 — AI organize: provider connection, session detection, organization plans, ask/auto modes, undo + activity log.
  3. M3 — Semantic search: index, natural-language answers, answer cards, temporal queries.
  4. M4 — Polish & ship: onboarding, settings, DMG signing/notarization, updater, performance pass.

11. Future phases (feature-level outline)

Phase 2 — Sync and portability

  • Notes folder can live inside a user's existing sync client folder (Google Drive, Dropbox, iCloud Drive) — the app must handle sync-induced file churn, conflicts (conflicted copy files), and partial availability.
  • First-class “Open existing library”: on a fresh Mac, install the app, point it at the synced root folder, and the full library (including rebuilding local indexes) comes up.
  • Conflict resolution UX for the same note edited on two machines.
  • Local model support (Ollama) as a second AI provider, fulfilling the FR-6.5 placeholder.
  • Optional Apple Notes importer if deferred from Phase 1.

Phase 3 — Cross-platform

  • Windows build, then Ubuntu/Linux. The Phase 1 design spec should note which stack choices help or hurt this (a legitimate input to open question 9.1, but it must not compromise NFR-7 on Mac).
  • Feature parity policy: capture/search everywhere; platform-native look per OS.

Phase 4 — Depth features (candidate pool, unprioritized)

  • Attachments and image OCR (“the whiteboard photo from Tuesday”).
  • Clipboard/menu-bar quick-capture and a global system-wide hotkey.
  • Browser extension / share-sheet capture.
  • Team/shared libraries.
  • End-to-end encrypted sync.
  • iOS companion app.
