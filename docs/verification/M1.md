## 3. FR-2.3 / NFR-3 — `kill -9` 1 s after typing → ≤ last 750 ms lost (scripted test)

**PASS** — the scripted test did not exist before this pass; it was added as
`make smoke` phases `kill` / `killcheck` (see commit "test(smoke): SIGKILL phase
proves the FR-2.3 bound").

What it does: ⌘N → retitle → type burst A → wait 1.4 s (past the 750 ms
debounce) → type burst B → print `SMOKE ready-for-kill` and park.
`Tools/smoke.sh` polls at 200 ms and sends **SIGKILL** there — no
`applicationShouldTerminate`, no flush, no cleanup. Then it relaunches on the
same root.

Observed:

```
SMOKE ok   kill-first-burst-flushed
SMOKE ok   library-opens-after-sigkill — notes=1
SMOKE ok   sigkill-file-exists — Kill test.md
SMOKE ok   sigkill-kept-debounced-burst
SMOKE ok   sigkill-file-not-truncated
SMOKE info last-burst-survived=false
SMOKE ok   sigkill-note-in-sidebar
```

Exactly the documented bound: the burst that had passed the debounce is on disk
byte-complete, the burst typed in the final instant is gone, and the library
opens cleanly after an unclean shutdown. Whether the last burst survives is
*reported*, never asserted — that is the ≤750 ms window FR-2.3 buys.

Supporting automated coverage: `AutosaveSchedulerTests` (suite "Autosave
scheduler (FR-2.3, NFR-3)") covers the timing state machine deterministically —
debounce, flush on note switch / resign / terminate, a keystroke landing
mid-write leaving the note dirty at the newer text, and terminate replaying
notes in dirty order (ADR-022). Phase `1`/`2` cover the *graceful* quit path
(`terminate-flush-finished`, `terminate-flushed-last-burst`).

## 6. NFR-1 / NFR-2 — keyword p95 < 100 ms at 5k/20k; launch-to-editable < 2 s

**PASS** for keyword search. **PARTIAL** for launch, on the measurement rather
than the number.

### Keyword search

`make bench ARGS="keyword --notes 5000"` — debug build, this machine:

```
corpus:   5000 notes generated in 776 ms
library:  5000 notes, 10.2 MB of Markdown
index:    rebuild 1.65 s for 5000 notes, database 54.9 MB

query shape          n     p50       p95       max      example
single word          40    23.6 ms   24.5 ms   25.6 ms  tokens
prefix               40    16.2 ms   16.7 ms   16.8 ms  docum
two words            40    14.4 ms   14.7 ms   15.6 ms  token budget
typo'd title         40    9.1 ms    9.4 ms    9.7 ms   cache bugdets 2696
code substring       40    6.5 ms    6.8 ms    6.9 ms   pplication/json

overall:  200 searches — p50 14.4 ms, p95 23.9 ms, max 25.6 ms
PASS      p95 23.9 ms < 100 ms (NFR-1)
```

The bench **exits non-zero** at p95 ≥ 100 ms, so it is usable as a gate. The
same budget is a failing test in CI: `SearchScaleTests` (suite "Search scale
(NFR-1, NFR-2)") gates 5,000 notes on a *debug* build and reports 20,000:

```
[search]  5,000 notes — index rebuild 2513 ms; 40 searches p50 17 ms, p95 29 ms, max 35 ms
[search] 20,000 notes — index rebuild 7962 ms; 20 searches p50 46 ms, p95 91 ms, max 100 ms
```

20,000 notes on a debug build is at 91 ms p95 — inside NFR-1 but with little
room; release is ~40 ms (`docs/core-api.md`). NFR-2's "degrade gracefully" is
what the looser 500 ms assertion in that suite encodes.

End-to-end through the UI, `make smoke` phase `search` prints the coordinator's
own backend timings on the 3-note corpus: `59.1 ms, 2.1 ms, 1.9 ms, 2.0 ms,
0.6 ms` (the first includes opening the index), plus the 80 ms debounce — well
inside FR-5.1's "<100 ms perceived".

### Scan

`make bench ARGS="scan --notes 5000"` — debug build:

```
library:  5000 notes, 16 folders, 10.2 MB
scan:     min 542 ms  median 548 ms  max 548 ms
rebuild:  min 1.63 s  median 1.66 s  max 1.70 s
total:    2.17 s (scan + rebuild, best of 3)
```

`ScaleTests` gates the 5,000-note scan + rebuild under 3 s on debug.

### Launch to editable

`LaunchClock` (the `XCTApplicationLaunchMetric` stand-in, ADR-023/`LaunchTimer`)
measured from the kernel's process start, release build, printed by every smoke
phase:

```
phase 1: didFinishLaunching=194ms windowVisible=250ms libraryOpen=254ms editorReady=254ms
phase 2: didFinishLaunching=176ms windowVisible=234ms libraryOpen=236ms editorReady=282ms
```

0.25–0.28 s against a 2 s budget — an 8× margin.

**Gap.** That is a two-note library. Launch is designed to paint from the
database and reconcile afterwards (ADR-023), so it should be flat in library
size, but nobody has measured launch on the 5,000- or 20,000-note corpus. →
**owner M4-07** (Instruments cold-launch profile, 20k degrade behaviour).

## 7. Notarized DMG of the M1 build installs on a clean user account

**FAIL — blocked, not broken.** Everything up to the signing step works.

```
$ make dmg
create-dmg produced no image; falling back to hdiutil.
Built build/Filaway.dmg (3.8M)

$ make notarize
BLOCKED: no 'Developer ID Application' certificate in the keychain.
         Enrol at developer.apple.com ($99/yr), then create the certificate in
         Xcode > Settings > Accounts. Override with FILAWAY_SIGNING_IDENTITY.
```

`Tools/notarize.sh` runs every precondition check and reports which one failed,
so it can be verified in a single pass once credentials exist (ADR-002, plan §8
risk #5). The bundle today is **ad-hoc signed** (`codesign -s -`), so Gatekeeper
on another machine will refuse it and `spctl -a -vv` cannot pass.

Note also that `create-dmg`'s Finder-window layout needs an unlocked GUI
session; on a locked screen its AppleScript times out and `make_dmg.sh` falls
back to `hdiutil`, which produces a working but unstyled image.

**Gap.** → **owner M4-05** (release pipeline), gated on the user enrolling in
the Apple Developer Program and installing Xcode. The same enrolment unblocks
the universal (arm64 + x86_64) build, which needs Xcode's `xcbuild` — today's
bundle is arm64-only, so "installs on a clean user account" is unverified on
Intel too.

## Not in the M1 DoD, verified anyway (M1-12)

`make smoke` phase `search` covers the new ⌘K surface end to end, on a
three-note corpus seeded on disk **before** the app launches (so it also proves
a cold launch indexes an unknown library): as-you-type hit counts, match and
snippet ranges, folder path, ↑/↓ clamping, ⏎ opening, the editor scrolling so
the match is on screen *and* the top of the note is not, a hit inside the note
already open, a misremembered title matching fuzzily, the empty query returning
Recents, "No matches", stale-query dropping, and Escape closing the panel and
returning first responder to the editor. 40 assertions, all green.
