## 0. A note on the smoke evidence below

`make test` is green on this branch (**734 tests**). `make smoke` was re-run on
2026-08-23 and **fifteen phases failed on the harness, not on the app**: after a
run that kills the app, macOS decides it has a crash history and opens *"Do you
want to try to reopen its windows?"* — an `NSAlert` shown **before**
`applicationDidFinishLaunching`, so the scene is never built and every phase
that types into the live `NSTextView` fails at `no MarkdownEditorView`. The fix
is `-ApplePersistenceIgnoreState YES` plus deleting
`~/Library/Saved Application State/com.tejaspanse.filaway.savedState`; it landed
on `main` in `Tools/smoke.sh` and reaches this branch on the next merge.
`filaway-bench launch` applies the same fix and gets windows reliably
(`docs/verification/M4-perf.md` §1.3), which is what proves the cause.

So: every smoke phase named below is cited as **the coverage that exists**, from
the runs that produced it before this branch, not as a green run taken today on
this branch. Re-run `make smoke` after merging `main` to confirm.

## 1. FR-5.1 / 5.2 / 5.3 — the two DoD queries, and the gate

### 1.1 / 1.2 The two named queries — **PASS**

Both DoD sentences exist **verbatim** as fixtures and as smoke assertions:

* `Tests/FilawayCoreTests/AnswerFixtures.swift`: scenario `curl-code-card`,
  `query: "curl command to fetch documents"`; scenario `temporal-auth`,
  `query: "the thing I edited two days ago about auth"`.
* `Features/Search/SemanticSmokeCheck.swift`: `static let query` and
  `static let temporalQuery` are those same two strings, driven end to end
  through the real ⌘K panel in the `semantic` smoke phase.

The `semantic` phase asserts what the user sees: `answer-card-arrives`,
`card-came-from-claude`, `card-snippet-is-the-command`, `card-is-a-code-block`,
`card-source-is-the-note`, `card-source-label-has-the-folder`,
`card-is-selected-first`, `card-note-not-repeated-below`,
`copy-returns-the-snippet`, `copy-reaches-the-pasteboard`,
`temporal-search-settles`, `temporal-query-filters-by-edit-time`.

Offline, the prompt→tool contract is pinned by `AnswerExtractorTests.swift`,
`@Suite("Answer goldens (M3-05)")`: *"curl command to fetch documents → the code
card of Figure 2b"*, *"a temporal query keeps its filter and comes back as a note
list"*, *"nothing fits → no card, and the list still stands"*, *"a fence is
trimmed to the line that was asked about"*, *"an invented command never reaches
the card"*, *"no committed answer fixture carries excluded text (FR-4.5)"*.
Fixtures: `Tests/Fixtures/ai-recordings/search/` — five files, Haiku 4.5.

The benchmark's own corpus asks the same questions in the user's words:
`Tests/Fixtures/queries/dev.json` has `curl-staging` — *"the curl I used to
fetch docs from staging"* → `Commands/curl/Staging docs endpoint.md` — and
`t-auth-2d` — *"the auth thing from two days ago"* →
`Debugging/network/Auth API 401 session.md`, with the expected date range
asserted against `TemporalQueryParser`.

### 1.3 The ≥ 90% gate — **PASS, 95%**

`RetrievalGateTests.swift` runs the **real bundled bge-small** over the whole
302-note corpus in ~11 s on every `swift test`, and asserts: no missing expected
paths, every outcome used vectors, note top-1 ≥ 0.90, answer top-1 ≥ 0.85,
MRR@10 ≥ 0.90, top-3 ≥ 0.95, p95 < 1 s, negative rejection ≥ 0.75.

It does **not** silently self-skip: the model is committed
(`Sources/FilawayCore/Resources/Models/bge-small-en-v1.5-s256-b1.mlpackage`,
66 MB, a plain git blob, no LFS) and `EmbedderFactoryTests` asserts
unconditionally that the bundle contains it. It is skipped only by an explicit
`FILAWAY_SKIP_SLOW_TESTS=1`.

Measured 2026-08-23, `filaway-bench retrieval --embedder bge`:

| Category | n | top-1 | top-3 | MRR@10 | answer | p50 | p95 |
|---|--:|--:|--:|--:|--:|--:|--:|
| command | 6 | 100% | 100% | 1.000 | 100% | 14 ms | 19 ms |
| paraphrase | 56 | 95% | 100% | 0.970 | 93% | 14 ms | 20 ms |
| temporal | 8 | 88% | 100% | 0.917 | 88% | 6 ms | 9 ms |
| typo | 7 | **100%** | 100% | 1.000 | **100%** | 14 ms | 16 ms |
| **all positives** | **77** | **95%** | **100%** | **0.970** | **94%** | **14 ms** | **19 ms** |

Negatives: 12, rejected 100%. Against M3-07's 91% / 97% / 0.939 / 90%.

`RetrievalBenchmarkTests` runs the same pipeline on a model-free
`HashedEmbedder` on every machine in ~1.7 s, so the corpus, the mtime stamping,
both arms, RRF, the temporal filter, the answer step and every metric are
exercised even where Core ML is not.

Temporal parsing (FR-5.3) has its own 24-test suite,
`TemporalQueryParserTests.swift`, including *"the answer moves with the injected
clock"* and *"phrases that only look temporal are left alone"*. Chunk ranges
(FR-5.2's scroll-to) are covered by `ChunkerTests` — *"every chunk's range points
at the text it came from"*, *"ranges are UTF-16 correct across astral
characters"* — and `HybridSearchTests` *"the best chunk carries a range that
opens the note at the command"*.

### 1.4 Manual live spot check — **BLOCKED (no key)**

Every answer fixture is hand-authored. The 94% answer accuracy above is the

## 2. FR-5.4 — an edit shows up; a rebuild completes

### 2.1 An edit is retrievable — **PASS**

`HybridSearchTests.swift`: *"an edit is retrievable as soon as it is indexed
(FR-5.4)"*. `IndexerTests.swift` covers the mechanism —
*"incrementalReindex"*, *"insertionShiftsOrdinalsWithoutReembedding"*,
*"reindexingUnchangedNoteIsFree"*, *"the debounce loop coalesces a burst of
saves"*, *"catchUp indexes only what is stale"*, *"statusReportsProgress"*.

The app wiring is real: `AppModel` feeds `autosave.onSaved` →
`semanticSearch.noteSaved(_:)` and the watcher →
`semanticSearch.libraryChanged(_:)`.

### 2.2 …within 5 s — **PARTIAL**

No test asserts the bound. The evidence is arithmetic over measured parts:

```
autosave debounce            750 ms   (AutosaveScheduler.defaultDebounce)
indexer debounce           2 000 ms   (Indexer.Configuration.debounce)
re-index one edited note       9 ms   (filaway-bench index, 5k realistic notes)
                          ---------
                           ~2.8 s     against FR-5.4's 5 s
```

The 9 ms is real and measured at both scales (8.9 ms at 5,134 notes, 11.9 ms at
20,234 — `docs/verification/M4-perf.md`), and it is small because the indexer
diffs chunks by `textHash` and re-embeds only what changed. But the *end-to-end*
bound is unasserted, and the two debounces are settings-visible, so a future
change to either could break FR-5.4 with every test still green. **A test that
types, waits, and re-queries under a bounded clock would close this.**

### 2.3 A timed 5k rebuild — **PARTIAL**

Bench-only, and the number is good:

```
filaway-bench index --root <5k realistic notes>
build:    51.99 s for 5134 notes (98.7 notes/s), 10 421 chunks
```

There is no `@Test` that times it. `ScaleTests.scanAndRebuild()` times the
*metadata and FTS* rebuild of 5,000 notes against a 3 s budget, which is a
different rebuild — the semantic one is a minute of Neural Engine work and would
be a poor unit test. Leaving it to the bench is the right call; what is missing
is a CI step that runs the bench, the way `filaway-bench keyword` is run.

### 2.4 `Settings → Rebuild index` — **PASS** (closed after this audit was written)

Closed by the M4-02 settings merge: `GeneralSettingsView` now has a live
"Rebuild…" button calling `model.rebuildIndex()` →
`SemanticSearchCoordinator.rebuildAll()`, with `IndexStatus` progress and a
disabled state while running; the `settings-wiring` smoke phase covers it.

## 4. NFR-1 — latency

### 4.1 Semantic p95 < 5 s — **PARTIAL**

The offline half is measured and is three orders of magnitude inside budget:

| Corpus | p50 | p95 |
|---|--:|--:|
| Dev corpus, 302 notes, bundled model | 14 ms | 19 ms |
| 5,000 realistic notes, bundled model | 19 ms | 20 ms |
| 20,000 realistic notes | 27 ms | 42 ms |

`RetrievalGateTests` asserts p95 < 1 s on every `swift test`;
`filaway-bench semantic` fails above `--budget-millis 500`; the `semantic`
smoke phase asserts `semantic-under-the-5s-budget` end to end with a scripted
provider.

**Why partial:** the Claude answer step — which owns essentially the entire 5 s
budget — has never been timed against the real API. The DoD names
`filaway-bench semantic --live`; **that flag was never implemented**, and
neither was the `filaway-bench prompts` subcommand plan §1 mentions. What
exists is `--answer replay|local|none` on `filaway-bench retrieval`. Either
build the `--live` flag or amend the DoD to name the command that exists; the
current text points at nothing.

### 4.2 Keyword still < 100 ms — **PASS**

CI runs `swift run filaway-bench keyword --notes 5000`, which exits non-zero at
p95 ≥ 100 ms. `SearchScaleTests` asserts it as a test too — *"Keyword search over
5,000 notes stays under 100 ms at p95"* (measured 2026-08-23: p50 17 ms, p95
29 ms) — and *"Keyword search over 20,000 notes degrades gracefully"* (p50 47 ms,
p95 93 ms, budget 500 ms).

M4-07's typo repair does not touch this path: ⌘K as-you-type goes through
`SearchService`, not `HybridSearch`.

## 5. NFR-2 — 20,000 notes

### 5.1 / 5.2 Memory, and the lazy matrix — **PASS**

Measured on 20,234 realistic notes (`docs/verification/M4-perf.md` has the full
table):

| | 5,134 notes | 20,234 notes |
|---|--:|--:|
| Chunks | 10,421 | 41,071 |
| Resident vector matrix | 8.4 MB | **32.9 MB** |
| Process growth when it loads | +16.8 MB | **+38.0 MB** |
| Lazy load, first semantic query | 44 ms | **133 ms** |
| Derived database | 23.6 → 43.1 MB | 89.2 → 169.5 MB |

Against NFR-2's ~200 MB budget, the semantic index costs **38 MB** at 20,000
notes — and only for a user who presses ⌘K, because `VectorStore` loads nothing
until the first semantic query. `VectorStoreTests.memoryAtScale()` asserts the
20,000-chunk budget on every slow-test run.

The alarming numbers in M3-03 (273 MB) came from `SyntheticCorpus`, which writes
a fenced code block every fifth paragraph and produces 17 chunks per note
against a realistic 2.0 (ADR-048). Both corpora are legitimate;
`SyntheticCorpus` stays the filesystem and database fixture, and NFR-2 is
reported against notes a person would write.

### 5.3 The UI stays smooth — **PARTIAL**

There is now a real measurement of the part that was most at risk — searching
*while* the first-launch index builds (M4-07):

```
20,234 notes, 902 searches at .userInitiated while the indexer ran at .utility
latency:  p50 49.7 ms, p95 78.7 ms, max 106.4 ms
partial:  25% in: 10 441 chunks · 50%: 20 811 · 75%: 30 920 — never zero results
```

So the four-minute first index is background work that costs a query 50 ms, and
⌘K improves steadily while it runs rather than being empty until it finishes.

**Why partial:** *scrolling* a 20,000-row sidebar is still unmeasured, and it is
a different question from query latency — `SidebarView` builds a `Folder` tree
from `AppModel.tree`, and nothing profiles it. Frame timing needs Instruments,
which needs Xcode (plan §8). The honest statement is "the parts that can be
measured headlessly are comfortable; the scroll is unverified".

### 5.4 Exclusions reach the index — **PASS**

Not in the DoD's words but part of what makes the index trustworthy:
`Indexer.index(_:)` purges chunks for an excluded note, `HybridSearch.Options`
carries the `ExclusionFilter` into the vector top-k gate, and
`OrganizeExclusionTests` plus the fixture-wide leak scan
(`AIHarnessTests.exclusionsNeverRecorded`) prove nothing from an excluded folder
can be embedded, ranked or put in a prompt.
