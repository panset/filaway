**Task:** plan §3, the **DoD M2** list. **Date:** 2026-08-23.
**Machine:** Apple M2, 16 GB, macOS 26.1, Swift 6.0.3, no Xcode, **no API key**
(plan §8).

**Verdict: 14 PASS, 5 PARTIAL, 1 FAIL, 1 BLOCKED of 21 clauses.** The one
outright failure is FR-4.4's raw session text on the automatic path — a known
structural gap, recorded in `docs/organize.md` since M2-12 and not fixed here.
The blocked item is the live pass with a real key, which no work on this machine
can unblock. Every partial is a *coverage* gap, not a behaviour gap: the
behaviour is implemented and proven at one level and unproven at another.

Evidence is named precisely — file plus the test's own name — so each row can
be re-run rather than re-argued.

## 1. FR-3.1 / FR-3.2 — sessions and the race matrix

### 1.1 Typing → idle interval → the session ends — **PASS**

`Tests/FilawayCoreTests/SessionTrackerTests.swift`, `@Suite("Session rules
(FR-3.1)")`: *"a session starts on the first edit, not on scrolling"*, *"the
idle timer ends the session, and the end time is the deadline"*, *"scrolling and
selecting reset the idle timer (FR-3.1)"*, *"the idle interval is clamped to
FR-3.1's 1–15 minutes"*, *"switching notes keeps the session alive but does not
touch the note"*, *"touched notes accumulate in first-touch order, without
duplicates"*, *"a session nobody typed in is discarded, not organized"*.
`@Suite("SessionTracker (M2-03)")` adds *"the armed timer fires the session with
no explicit tick"*, *"the flush hook runs before the ended event (ordering
contract)"* and *"shortening the idle interval in Settings applies to the
running session"*.

Implementation: `Session/SessionTracker.swift` (actor), `SessionMachine.swift`,
`SessionClock.swift`.

### 1.2 ⌘-Tab away → the card appears — **PARTIAL**

The *rule* is fully tested at Core level: `SessionTrackerTests` covers *"⌘-Tab
ends the session but the pipeline waits out the grace (amendment 2)"*, *"a
second ⌘-Tab does not push the deadline further out"*, *"coming back to the app
does not, by itself, cancel the grace"*, *"⌘-Tab with no return files the
session once the grace expires"*, *"quitting ends the session immediately, with
no grace"*, *"quitting during the grace fires the pending session at once"*, *"a
zero grace ends the session immediately on ⌘-Tab"*.

The *card* is proven by the `organize` smoke phase —
`Features/Organize/OrganizeSmokeCheck.swift`: `card-appeared`,
`card-is-a-question`, `card-summary-is-the-plan`, `card-has-a-plan`.

**Why partial:** the smoke phase does not ⌘-Tab. It calls
`OrganizeCoordinator.endSessionNow(noteID:endedAt:)` so the session ends at the
fixture's recorded instant and the replay key matches. The app-level hooks
(`appDidResignActive()`, `windowClosed()`, registered in `FilawayApp.swift`) are
therefore wired but not exercised end to end. Closing this needs either a
synthetic ⌘-Tab (no XCTest UI without Xcode, plan §8) or a smoke phase that
posts `NSApplication.didResignActiveNotification` itself — the latter is
cheap and worth doing.

### 1.3 Resuming typing before apply cancels / supersedes — **PASS**

`SessionTrackerTests`: *"typing inside the grace supersedes the end silently"*,
*"scrolling inside the grace also cancels it"*, *"⌘-Tab schedules, typing in the
grace cancels, and nothing is filed"*.

`Tests/FilawayCoreTests/OrganizerTests.swift`, `@Suite("Organizer concurrency
(FR-3.2, M2-05)")`: *"typing during an in-flight request cancels it and leaves
the baseline alone"*, *"typing in a note with a plan on screen withdraws it"*,
*"typing in the plan's target note also withdraws it"*, *"a newer session over
the same notes supersedes the pending plan"*, *"the cancelled note rides along in
the next session, from the same baseline"*.

### 1.4 The race matrix — **PASS**

All in `OrganizerTests.swift`. **CAS:** *"accept after the note changed
underneath is stale, and writes nothing"*; and in `ApplyTests.swift` *"a
compare-and-swap miss changes nothing at all"*, *"a segment that is no longer
verbatim is a precondition miss, not a guess"*, *"a plan that no longer validates
is refused before anything is written"*. **Baseline advance:** *"session end → a
proposal, and the baseline does not move yet (ask mode)"*, *"session end →
applied immediately (auto mode), baselines advance to what is on disk"*,
*"nothing to do advances the baseline so the same text is never re-sent"*,
*"dismiss advances the baseline to the text the plan was made against"*,
*"accept applies the plan and advances every baseline it touched"*.
**Queueing:** *"two sessions over different notes run at the same time"*, *"two
sessions sharing a note never overlap"*, *"no more than two requests run at
once"*, *"no effective delta → no request at all"*, *"a session with no
surviving notes is skipped"*. **Edited plans:** *"an edited plan is re-validated
before it is applied"*, *"an edited plan that names a note that does not exist is
refused"*.

## 2. FR-4.1 – FR-4.5 — plans, both modes, the closed set

### 2.1 Both modes on the golden scenarios, replay — **PASS**

`Tests/FilawayCoreTests/OrganizeGoldenTests.swift`, `@Suite("Organize goldens
(M2-06)")`. `OrganizeGolden.scenarios` defines **nine**: `new-note`,
`merge-code-block`, `retitle-untitled`, `new-folder`, `nothing-to-do`,
`convergence`, `excluded-folder`, `invalid-action-dropped`,
`summary-no-longer-matches`. *"the scenarios cover what plan §3 asks of M2-06"*
asserts the required eight by name and `count >= 8`; *"every golden scenario
replays end to end"* is parameterised over all nine.

Both modes end to end through the production applier, log and queue:
`OrganizeWiringTests.swift`, `@Suite("Organize app wiring (M2-12)")` — *"ask
mode: propose, accept, apply, undo — production applier, log and queue"*, *"auto
mode applies without asking, and the baseline advances"*.

In the shipped app: smoke phases `organize` (ask), `organize-auto`,
`organize-offline` (`Tools/smoke.sh`).

Fixtures: `Tests/Fixtures/ai-recordings/organize/` — 13 files. Eight cover the
nine golden scenarios, because **`merge-code-block` and `excluded-folder`
deliberately share a key**: the second scenario's whole assertion is that adding
an excluded note leaves the request byte-identical (*"the excluded note leaves
no trace at all — the request is byte-identical without it"*).

### 2.2 A live pass with a real key — **BLOCKED (no key on this machine)**

Every committed response is hand-authored. `OrganizeGoldenTests.swift`'s header
says so, and names the command to fix it:
`FILAWAY_AI_MODE=record swift test --filter "Organize goldens"`. The requests
are *not* hand-authored — they are captured from the real builders — so what is
untested is the API's acceptance of them, not their content. The specific
assumptions at risk are enumerated in **`docs/prompts.md` §4** (strict `anyOf`,
`["integer", "null"]`, adaptive thinking with a forced tool, Haiku latency).

This is the single largest unknown in M2 and it cannot be closed here.

### 2.3 No action outside the closed set passes the validator — **PARTIAL**

*Structurally* proven, `OrganizePlanTests.swift`: *"the schema names exactly the
closed action set"*, *"the schema rejects what the codec would reject"*,
*"unknown and unreadable actions are reported, the rest survive"* (feeds
`deleteEverything` and checks the reason names the closed action set), *"no
action in the closed set can delete user text (FR-4.4)"*, *"a segment move
carries the text so nothing can be lost"*, *"every encoded action validates
against the schema"*.

*Property-style* fuzzing exists but over the wrong axis:
`OrganizeValidatorTests.swift` has *"a plan built from random unknown ids never
validates"* (200 iterations, `SplitMix64(seed: 0xF11A_1A17)`) and *"random
folder paths deeper than the cap never validate"* (100 iterations) — both fuzz
**ids and paths**, not **action kinds or malformed payloads**.

**Why partial:** plan §3 M4-08 owns "malformed-plan fuzz (validator rejects)",
so the gap is scheduled rather than forgotten. Until it lands, the claim is
"every action the decoder can produce is in the closed set", which is a weaker
statement than "no adversarial JSON gets through".

### 2.4 Excluded-folder content never reaches a request — **PASS**

Two independent assertions, one of them over *every* committed fixture:

* `AIHarnessTests.swift` — *"no excluded note ever appears in a recorded request
  (FR-4.5)"* iterates `AITestPaths.recordingStore.all()`, runs
  `ExclusionFilter.leaks(in:bodies:notes:)`, and additionally greps for the
  sentinel strings `"Salary"` and `"12345"`.
* `OrganizeGoldenTests.swift` — *"no golden request contains a byte of the
  excluded folder (FR-4.5)"*: `"88888"`, `"Pay review"`, `"compensation"`, the
  excluded note's UUID, `"Private"`.

Unit level: `OrganizeExclusionTests.swift`, `@Suite("Exclusion filter
(FR-4.5)")`, eight tests including a **negative control** — *"the leak detector
actually detects a leak"*, which is what stops the other seven from being
vacuous. Plus `OrganizerTests`: *"an excluded note in the session never reaches
the provider"*, and `OrganizeContextBuilderTests`: *"an excluded folder is not
named, let alone quoted (FR-4.5)"*.

This is the best-covered clause in M2, and rightly: it is the one where a
regression is a privacy incident rather than a bug.

## 3. FR-4.3 / FR-4.4 — Activity, Undo, retention

### 3.1 Undo 10 deep, byte-identical — **PASS**

`ActivityUndoTests.swift`, `@Suite("Undo")`, *"ten stacked events unwind to a
byte-identical tree at every step"*: fingerprints the whole tree before each of
ten applies, then asserts LIFO order, `outcome == .complete`, and
`fingerprint() == fingerprints[index]` **at every step** — not just at the end —
finishing with `undoableEvents().isEmpty` and `UndoError.nothingToUndo`.

Around it: *"undo of a created note moves it to the Trash, never deletes it"*,
*"undo of a `moveSegment` that trashed its source writes the source back"*, *"an
edit elsewhere in the note survives the reverse patch"*, *"an edit the patch
cannot unpick becomes a marked conflict block, never a loss"*, *"a later event
touching the same note blocks an out-of-order undo"*, *"events that touch
different notes may be undone in any order"*, *"an event can only be undone
once"*.

In the app: smoke `organize` — `undo-completed`, `undo-restored-the-target`,
`undo-restored-the-source`; smoke `organize-auto` —
`card-undo-restored-the-session-note`.

### 3.2 Activity shows the diff — **PARTIAL**

The data is fully covered. `ActivityLogTests.swift`: *"diff(for:) is a per-note
before/after over the body, front matter aside"*, *"a created note diffs as pure
insertion; a trashed one as pure deletion"*, *"a move shows up as a relocation,
not as a rewrite"*, *"an event carries its plan, prompt version, model and
summary"*, *"the log lists events newest first and pages with a cursor"*.
`ActivityDiffTests.swift` (`@Suite("Text diff")`, 13 tests) includes *"reversing
a diff and replaying it restores the original"*. The smoke `organize` phase
asserts `activity-has-the-event`, `activity-keeps-the-summary`,
`activity-has-a-diff`.

**Why partial:** nothing opens the **Activity window** itself. ⌥⌘A,
`ActivityWindowView`, `ViewChangesSheet`, `EditPlanSheet` and `DiffView` have no
test and no smoke check — the M2-10 UI is verified by eye only. A smoke phase
that opens the `Window("Activity")` scene and reads its rows would close this;
it needs no synthetic events, since the phase already applies a plan.

### 3.3 29 days retrievable, 31 days pruned — **PASS**

`ActivityLogTests.swift`, *"raw session text survives 29 days and is pruned at
31"*, driving an injected `ApplyClock` through `ApplyHarness(clock:)`:
`advance(29 days)` → `sessionTextsPruned == 0` and the text still readable;
`advance(2 more)` → `sessionTextsPruned == 1`, `sessionText(for:) == nil`, and
`eventCount() == 1` — the event survives, only its raw text goes. Companion:
*"before/after images are kept while an event is undoable"*.

### 3.4 FR-4.4's raw session text is recorded at all — **FAIL**

`docs/organize.md` § "Known gap", verbatim:

> The organizer calls `PlanApplying.apply(_:)`, which has no room for the
> session's raw text, so **FR-4.4's raw session text is not recorded on the
> automatic path** — `PlanApplier.apply(_:sessionText:)` supports it and
> `ActivityLog` stores and prunes it, but nothing between the tracker and the
> applier carries the text.

So §3.3's test passes because it calls `PlanApplier.apply(_:sessionText:)`
**directly**. On the shipping path no session text is ever stored, and the
Activity window's disclosure is therefore always empty. FR-4.4 says content is
never destroyed; the *files* satisfy that (nothing is hard-deleted, §5.2), but
the "raw text kept for 30 days" half of the amendment-1 promise is not being
kept.

**The fix is one of two, both small:** a second parameter on the
`PlanApplying.apply` contract (ADR-033), or a setter on `ActivityLog` the
coordinator calls after apply. Neither was done here because
`Organize/ApplyModel.swift` is another agent's file this milestone. **This is
the one M2 clause that is failing rather than merely unproven, and it should be
closed before the dogfood week.**

## 4. FR-6.1 / FR-6.4 — degradation

### 4.1 The error taxonomy — **PASS**

`AIProviderTests.swift`, `@Suite("ClaudeProvider over a stubbed transport",
.serialized)`: *"401 maps to invalidKey and is never retried"*, *"429 waits for
retry-after, then succeeds"*, *"429 that never clears gives up after
maxAttempts"*, *"529 backs off exponentially with jitter"*, *"a URLError becomes
.network and is retried"*, *"a timeout is its own case"*, *"400 maps to
badRequest"*, *"404 maps to modelNotFound and names the model"*, *"no key at all
is notConfigured, and nothing is sent"*, *"a body that is not JSON is
malformedResponse"*, *"validateKey hits GET /v1/models"* (FR-6.1, amendment 4),
*"validateKey on a bad key is invalidKey"*. Plus `@Suite("Retry policy")`.

`OrganizerTests`: *"an offline provider queues the session and never blocks"*,
*"an invalid key queues; a bad request does not"*, *"a 400 fails outright rather
than queueing forever"*, *"the queue gives up after the attempt cap"*, *"a
refusal is reported, not retried"*.

### 4.2 Capture is unaffected — **PASS**

Smoke `organize-offline` (`FILAWAY_AI_FAIL=network`): `nothing-was-applied`,
`activity-is-empty`, `capture-still-works`.

### 4.3 Browse and keyword search are unaffected — **PARTIAL**

Nothing asserts it. `organize-offline` proves *capture* survives an outage but
runs no search and makes no sidebar assertion; the `search` phase runs with a
healthy replay provider. The claim is architecturally sound —
`SearchService.keyword` reads `MetadataStore.reader` and has no provider
reference at all, and the semantic path degrades through
`SemanticUnavailable` — but "sound by construction" is what every regression
was before it happened. **Three `check(...)` lines in `OrganizeSmokeCheck`'s
offline phase would close this**: one keyword search, one sidebar count, one
note open.

Also note that "airplane mode" is simulated by `FILAWAY_AI_FAIL`, never by a
real network cut (ADR-041 makes every smoke phase unable to reach the network at
all). The DoD's manual half stays manual.

### 4.4 The status pill is correct — **PARTIAL**

Core-level: **PASS**. `AIStateTests.swift`, `@Suite("AI status")` — *"errors map
onto the pill"*, *"a rate limit heals when its deadline passes"*, *"only the
offline-ish states queue work (FR-6.4)"*, *"labels are content-free"*, *"error
descriptions stay content-free and actionable"* (the last two are NFR-4
assertions as much as FR-6.4 ones). `SettingsConnectionTests.swift` walks the
whole connection state machine, and smoke `settings`/`settings2` drive it.

App-level: **not covered**. The strings the user actually sees live in
`Features/Organize/AIStatusIndicator.swift` — `"AI ready"`, `"AI queued · N"`,
`"AI offline"`, `"Key invalid"`, `"AI paused"`, `"AI off"` — and no test or
smoke `check(...)` reads them. The smoke asserts the *Core* `AIStatus.label`
(`"AI: offline"`), which is a different string. `"AI queued · N"` and
`"Key invalid"` have zero coverage.

Separately, the pill is **not in the toolbar yet** — `AIStatusPill` exists in
`Features/Settings/` and CLAUDE.md records the one-line `ShellView` insertion as
an open seam. So the DoD's "status pill correct" is unverifiable in the shipped
window until that lands (M4-06's owner).

### 4.5 No modal alert, ever — **PASS**

Smoke `organize-offline`: `no-modal-alert`, `no-card`,
`status-is-not-usable`.

### 4.6 Queued sessions survive a relaunch — **PASS**

`OrganizeWiringTests.swift`: *"a queued session survives closing and reopening
the database"*, *"re-enqueuing the same session updates its attempt count rather
than duplicating it"*, *"the queue comes back oldest first"*, *"an offline
organizer queues durably and drains when health returns"*. Storage:
`Organize/PendingSessionStoreGRDB.swift`.

## 5. NFR-3 — a crash mid-apply

### 5.1 Journal recovery — **PASS**

`ApplyRecoveryTests.swift`, `@Suite("Apply journal recovery")`, six tests:
*"a crash between operations rolls back to the before-images"*, *"a crash after
the last write but before the after-images rolls back"*, *"a crash after the
after-images are durable rolls forward"*, *"an error mid-apply rolls back
immediately, without waiting for a relaunch"*, *"a crash while trashing an
emptied source leaves the note recoverable"*, *"recovery is idempotent and
leaves nothing incomplete"*.

Each drives `ApplyHarness(failureHook: .crash(at:))`, then `restart()` and
`recover()`, and asserts the resolution, a byte-identical fingerprint,
`incompleteEvents().isEmpty`, `event.status == .rolledBack` and
`!event.isUndoable`.

**Caveat worth keeping:** `.crash` throws *without unwinding*, which is what a
power cut looks like from the journal's point of view, but it is an in-process
hook and not a `SIGKILL`. The only real-signal coverage in the repo is the
autosave path — smoke `kill` / `killcheck`, which SIGKILLs the app mid-burst and
proves on relaunch that at most one 750 ms debounce window was lost
(`sigkill-kept-debounced-burst`, `sigkill-file-not-truncated`). **No smoke phase
SIGKILLs the app mid-apply.** Given that the applier's transaction boundary is
the thing NFR-3 is about, a `kill-apply` phase would be the highest-value smoke
phase not yet written.

### 5.2 Never a hard delete — **PASS**

`ApplyTests.swift`, `@Suite("Plan apply")`: an emptied source goes to the
**Trash**, recoverable, and `ActivityUndoTests` *"undo of a created note moves
it to the Trash, never deletes it"*. `OrganizePlanTests` *"no action in the
closed set can delete user text (FR-4.4)"* proves it one level up: there is no
destructive action to plan.

### 5.3 Nothing but `.md` and folders in the user's tree — **PASS**

`ApplyTests.swift`: *"nothing but .md files ever lands in the user's tree"*,
plus the depth cap (`PathRules.maxFolderDepth`) and
`ActivityUndoTests` *"undoing an apply leaves no stray files and no third folder
level"*.

## 6. What to do next, in order

1. **Close FR-4.4's raw session text** (§3.4). It is the only FAIL, it is a
   one-parameter change, and the dogfood week is exactly when someone will want
   to see what they wrote before the AI moved it.
2. **A `kill-apply` smoke phase** (§5.1). The recovery logic is well tested
   against a simulated crash; the thing NFR-3 promises is behaviour under a real
   one.
3. **Three `check(...)` lines in `organize-offline`** for browse and keyword
   search (§4.3), and a smoke phase that opens the Activity window (§3.2).
   Both are cheap.
4. **Assert the app-level pill strings** (§4.4), once the pill is in the toolbar.
5. **Malformed-plan fuzz** (§2.3) — already scheduled as M4-08.
6. **The live pass** (§2.2) the day a key exists, following
   `docs/prompts.md` §5.
